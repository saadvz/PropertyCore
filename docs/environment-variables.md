# Environment variables

Every Property Core flow runs in one Node service, so they share one set of environment variables. The
`TOURCORE_*` names are kept as they are, because live deployments, `.env` files and saved secure-setup values
use them. The repository rename to Property Core (#179) did not change them.

Developer values live in `.env` (see [`.env.example`](../.env.example)). Hosted Railway sets the first four on
the service. A parked Tour Core install, Grok-managed or self-hosted, puts its credentials on Tour Core's secure
setup page instead (see [the Tour Core guide](tour-core/README.md)). For the hosted multi-tenant service, see
also [`hosted-multitenancy.md`](hosted-multitenancy.md) and [`deployment.md`](deployment.md).

| Variable | Used when | What it does |
| --- | --- | --- |
| `TOURCORE_DEPLOYMENT_MODE` | All. Default `LOCAL_DEVELOPER` | `LOCAL_DEVELOPER`, `GROK_MANAGED_P0`, `SELF_HOSTED`, or `HOSTED_RAILWAY_P0`. The last is set on our Railway service, not in a landlord's `.env`. |
| `TOURCORE_HOME` | All. Required on hosted | Records folder. Local default is `./tourcore-data`. On Railway this must be the volume, usually `/data`. |
| `TOURCORE_RESTORE_UPLOAD_MAX_BYTES` | Restore upload | Maximum portable-backup upload in bytes. 50 MB by default (TOURCORE_RESTORE_UPLOAD_MAX_BYTES), which is 50_000_000 bytes. The refusal states that cap in decimal MB, rounded down. A larger upload returns 413 and states this cap. An invalid value keeps the default. |
| `RAILWAY_VOLUME_MOUNT_PATH` | Railway injects it | The volume mount (usually `/data`). When present, `TOURCORE_HOME` must be inside it. Do not set this in a local `.env`. |
| `TOURCORE_ALLOW_EPHEMERAL_STORAGE` | Hosted demos only | Set to `1` to start even if `TOURCORE_HOME` is not on a persistent volume. Data is lost on the next deploy. **Never set this on a live service.** Local `npm run setup` ignores it. |
| `PUBLIC_BASE_URL` | Self-hosted and local tunnels | Public https origin that reaches this process. Railway derives it from `RAILWAY_PUBLIC_DOMAIN`. |
| `PORT` | Railway | Listen port. Railway sets it. `HOSTED_RAILWAY_P0` does not fall back to 4321. |
| `CLEANER_CORE_STALE_AFTER_MS` | Cleaner Core freshness | Optional. Milliseconds before a watched booking feed is stale. Default is `10800000` (three hours, three missed hourly Guesty Lite polls). A fetch exactly that old is still fresh. Used only when the drive watches freshness. |
| `CLEANER_CORE_LIVE_SMS` | Cleaner Core live texts | Off unless `1` or `true`. With it off, the cleaning number sends nothing. Scratch smoke does not use it. |
| `CLEANER_CORE_GROUP_CHAT` | Cleaner Core group thread | On unless `0` or `false`. The host is in that thread from the texting setup step and does not text YES. The approved cleaner replies YES. The door code stays a private text to that cleaner. A live group send still needs `CLEANER_CORE_LIVE_SMS`, the host's confirmed phone, and each member's YES. |
| `CLEANER_CORE_SCRATCH_TOOLS` | Cleaner Core Scratch QA | Off unless `1` or `true`. With it on, the cleaning chat lists tools to reset Scratch, read the inbox and outbox, send a test text, and record a delivery. They run only for a Scratch address whose saved numbers are all 555 test numbers. The outbox lists every text. When live texts are on, those texts also go to the allowlisted 555 numbers. |
| `CLEANER_CORE_SMS_ALLOWLIST` | Legacy approval of a host's phone | Cleaner Core no longer decides who is texted from this list: consent is per account (see `CLEANER_CORE_LANDLORD_PHONE`). For an account with no confirmed phone, such as one made in `/admin`, a host phone on this comma-separated list counts as confirmed, and `*` counts any number except this service's own lines. Tour Core's touring texts still go only to numbers this list allows. |
| `CLEANER_CORE_LANDLORD_PHONE` | Cleaner Core texting consent | The landlord's phone, confirmed with a code at sign-up. Nobody on the account is texted until the host saved in setup is this phone. Then the cleaner and each contact the host saved get one opt-in text, and nothing else until their own YES. STOP and HELP still win, and this service's own numbers are never texted. On the multi-tenant service each tenant's desk gets its own from the account and a process value is ignored; on a single-host deployment the operator may set it. |
| `CLEANER_CORE_MCP_TOKEN` | Cleaning scheduler chat | Credential for `/mcp/cleaner-core`. It is not the Tour Core connector credential. The chat is off until this is set and `CLEANER_CORE_ENABLED` is on. |
| `CLEANER_CORE_TWILIO_ACCOUNT_SID` | Cleaner Core Twilio | Account SID for the cleaning number. Set it on the existing Railway service. A bot never asks for it. |
| `CLEANER_CORE_TWILIO_AUTH_TOKEN` | Cleaner Core Twilio | Auth token for the cleaning number. Set it on the existing Railway service. A bot never asks for it. |
| `CLEANER_CORE_TWILIO_PHONE_NUMBER` | Cleaner Core Twilio | The cleaning number. Texts sent to this number are handled by Cleaner Core, even if they arrive on `/webhooks/twilio`. |
| `FIXER_CORE` | Fixer Core on the multi-tenant service | Off unless `1` or `true`. With it on, `set_flows` can turn Fixer Core (`fixer`) on for a property, for Grok Bot and Muse only. Unset, a request to turn it on is refused with the plain line that it isn't available yet, and nothing about any property changes: Fixer Core stays off for new properties. The host can turn it off for a property at any time. It contacts a real pro and shares a real door code, so set it only after `docs/fixer-core-safety-gates.md` is green and Saad okays it. Voicemail on the line needs no variable of its own: it uses the line's Twilio account (`CLEANER_CORE_TWILIO_ACCOUNT_SID`, `CLEANER_CORE_TWILIO_AUTH_TOKEN`). |
| `HOURS_LOG` | The hours log on the multi-tenant service | Off unless `1` or `true`. With it on, `review_hours`, `export_hours` and `save_hours_settings` are listed for every agent on an account where any property runs a flow. The rows are rebuilt from the property's own records on every call; `hours.json` in the property's folder keeps only the host's settings and each month's confirmation, with the owner's actions it confirmed. Each flow also keeps its own record of the host's approvals (in `fixer.json`, `supply.json` and Cleaner Core's store, flag on or off), so an approval replaced before its month is confirmed still shows. It texts nobody and holds no Google or Microsoft token: the agent writes the host's own spreadsheet (Google Sheets, Excel or another) with its own connector, and asks the host where when none is connected. Owner rows come from the host's own standing lock code, on connected locks (#180). |
| `STAY_CHECK` | The nightly stay check's house rules on the multi-tenant service | Off unless `1` or `true`. With it on, `get_house_rules`, `save_house_rules` and `allow_for_stay` are listed for every agent on an account where any property runs a flow. The agent asks the host for their own house rules, with examples, and saves a check only for a rule it read back and the host agreed to. `stay-check.json` in the property's folder keeps the rules, the check time, per-stay allowances and the sightings each kind needs after false flags. It texts nobody. Camera and noise events come with the camera connection, and sending the alert waits on #250. |
| `BOOKING_PLATFORMS` | Booking emails from more platforms (#263) | Off unless `1` or `true`. With it on, `save_sources` takes `bookingEmails` (the platforms the host books on: Airbnb, Vrbo, Booking.com, their own booking site or Other, with each sender) and `shareSamples`; `get_state` and `check_now` return `bookingEmails`, naming only the senders the agent passes, and `waitingBookings`; and `read_booking_email` takes `extracted` and `email.authentication`. An email from any platform but Airbnb is read only from its saved sender, and changes nothing until the host says yes to that booking. Airbnb, Vrbo and Booking.com emails whose `Authentication-Results` sender check fails change nothing. Stays from every platform go in `booking-emails.jsonl`, marked with their platform. `hub.json` keeps `bookingSources` and `shareSamples`. Off, every property reads Airbnb's emails only, exactly as before. It texts nobody. |
| `CAMERAS` | The camera connection (#239) on the multi-tenant service | Off unless `1` or `true`. With it on, `connect_cameras`, `list_cameras`, `pick_cameras`, `disconnect_cameras`, `check_night`, `stay_timeline` and `pin_clip` are listed for every agent on an account where any property runs a flow, and `POST /webhooks/ring`, `/cameras/connect/<link>` and `/cameras/ring/linked` answer. The host signs in on Ring's own page; only the outdoor cameras they pick are read. Events go into the property's shared `visit-events/<YYYY-MM>.jsonl` (written under this flag whatever `VISIT_RECORDS` says). `cameras.json` in the property's folder keeps the picks, the consent time and notes waiting for the host. No image is kept; a clip is copied to `evidence/` only when the host pins it. A camera offline for 30 minutes is one note for the host. It texts nobody. Needs `CAMERA_TOKEN_KEY` and the three `RING_*` secrets; counting also needs `CAMERA_DETECTOR_MODEL`. |
| `CAMERA_TOKEN_KEY` | Seals each account's Ring tokens | 32 random bytes in base64. Without it, no Ring account can be connected. An environment secret, never in code or logs. |
| `RING_CLIENT_ID`, `RING_CLIENT_SECRET`, `RING_WEBHOOK_SECRET` | Ring's private developer app | From the Ring developer portal once the app is registered. Without all three, the camera tools say Ring isn't set up and the routes answer 404. Environment secrets only. |
| `CAMERA_DETECTOR_MODEL`, `CAMERA_DETECTOR_THRESHOLD` | The camera counting detector | The path to RF-DETR Medium's model file (open source, Apache-2.0), fetched once with `npm run cameras:get-detector -- --out <path>` (a pinned Hugging Face revision, checked by SHA-256; keep it on the data volume). With it set, each motion still during a stay is counted on this server with onnxruntime-node, on the CPU, and only the counts are kept: no image leaves the server and no key is needed. The threshold defaults to 0.35, a starting point the counting week replaces. Each count line names the threshold, so a change recounts as new lines. Without the model, counting stays off. `CAMERA_DETECTOR_MODEL=<path> npm run cameras:live-count -- <image.jpg> ...` tries it by hand. Installs skip onnxruntime-node's CUDA download (`.npmrc`). |
| `REMOTE_OVERSIGHT` | Remote oversight's expected visits on the multi-tenant service | Off unless `1` or `true`. With it on, `add_expected_visit`, `list_expected_visits` and `cancel_expected_visit` are listed for every agent on an account where any property runs a flow. The agent saves a visit the host expects from anyone (a property manager, a cleaner, a friend), from what the host says or a calendar invite, only after reading it back and the host agreeing. `oversight.json` in the property's folder keeps the visits and when each was flagged. A visit with no entry is flagged the same day: 1 hour after its window, or at 8 PM for an all-day visit. It texts nobody. Entry events come with the lock connection (#180), and sending the flag waits on #250. |
| `VISIT_RECORDS` | Visit records: arrival, departure and time on site | Off unless `1` or `true`. With it on, Cleaner Core and Fixer Core write to `visit-events/<YYYY-MM>.jsonl` in the property's folder (append-only: lock events, each text to and from the cleaner, the host and pros with digit runs and the door code taken out and no phone number, and each visit window as it was set or moved), and `list_visits`, `visit_health` and `name_lock_code` are listed for every agent on an account where any property runs Cleaner Core or Fixer Core. Visit records are rebuilt from the log on every read. Only with a connected lock: a cleaner not in 30 minutes after the expected time (15 on a same-day turnover) gets one text, and the host one note when the next check-in is at risk, on a no-show, on a failed arrival-day check, or when the cleaner's code opens the door outside a cleaning; a pro or crew not in by the start plus 30 minutes is one Fixer Core news line. Without a lock, nothing new is sent. The hours log uses measured visit times when a record has both ends. No tool writes a lock event: they come from the lock connection (#180). |
| `SMART_LOCKS` | Connected locks (#180) on the multi-tenant service | Off unless `1` or `true`, and it needs `SEAM_API_KEY` too. With both, `get_locks`, `connect_lock`, `save_locks`, `lock_settings` and the standing code tools are listed for every agent on an account where a property runs Cleaner Core or Fixer Core, and `POST /webhooks/seam` takes the lock partner's events. A property switches to connected locks only with the host's yes, every door the cleaner and pros use connected, and a working alerts routine. Each cleaner and pro then gets their own code per visit, kept sealed in `door-grants.json` with the account's own server key; lock events go to the property's `visit-events/<month>.jsonl`. With it off, or a property not switched on, every door code works exactly as before. Turned on only after the gates in `docs/cleaner-core-safety-gates.md` and `docs/fixer-core-safety-gates.md` are green and Saad okays it. |
| `GUEST_CODES` | Guest codes (#262) on the multi-tenant service | Off unless `1` or `true`, and it needs `SMART_LOCKS` on with the lock adapter too. With both, `get_guest_codes`, `guest_codes`, `make_guest_code`, `guest_code_link` and the lease tools are listed, the lock clock keeps each stay's code in step with `booking-emails.jsonl` and late checkouts, and `/locks/guest/<token>` serves the single-use page. Only a property on connected locks whose host chose automatic or ask gets guest codes; leases each take the host's yes. Kept in `guest-codes.json` (no code); codes sealed in `door-grants.json`. With it off, nothing changes. Turned on only after `SMART_LOCKS` is live, the guest-code gates are green and Saad okays it. |
| `SEAM_API_KEY` | The lock partner's API key, for the service's one workspace | A service secret, never a host's, never in code, a log or chat. Unset: no property is on connected locks. Use a sandbox workspace's key until the paid rollout. |
| `SEAM_WEBHOOK_SECRET` | Verifies the lock partner's webhooks (`whsec_…`) | A service secret. Unset: every lock webhook is refused, so no event is stored and no alert goes. |
| `PACKAGE_ARRIVALS` | Package arrivals on the multi-tenant service | Off unless `1` or `true`. With it on, `check_packages`, `mark_package_seen`, `plan_bring_in`, `mark_brought_in` and `save_package_settings` are listed for every agent on an account where any property runs Supply Core. Expected deliveries are read from Supply Core's placed orders on every call; `packages.json` in the property's folder keeps only when each was seen and how, the bring-in visit, when it was brought in, the host's bring-in hours and default person, and which flags the host was told. A package expected and not seen by 9 PM local on its day is flagged once. The bring-in person must be saved for the property as the cleaner, a co-host or an assistant, and have said YES. It texts nobody: the bring-in code waits on the smart-lock connection (#180), and camera confirmation on #239. |
| `GUEST_MESSAGES` | Guest messages on the multi-tenant service | Off unless `1` or `true`. With it on, `get_guest_facts`, `save_guest_facts`, `read_guest_message` and `save_guest_reply` are listed for every agent on an account where any property runs a flow, and Cleaner Core lists `set_late_checkout`. The agent passes each Airbnb guest-message email it reads from the host's mailbox; Property Core returns the guest's words, the stay and the house facts that answer them, and the agent drafts a reply from only those. In the property's folder, `guest-facts.json` keeps the host's house facts for guests, `guest-messages.jsonl` (append-only) keeps each message taken with door codes removed, each approved or skipped reply and each late checkout allowed, and `guest-approvals.json` keeps pending reply approvals. Nothing reaches a guest from Property Core: the host pastes each approved reply into Airbnb. Sending through Guesty or Hospitable waits on #239. |
| `CLEANER_CORE_MULTI_TENANT` | Multi-tenant Cleaner Core | Off unless `1` or `true`. With it on (on `HOSTED_RAILWAY_P0`), one service serves every host on Grok, Claude, and ChatGPT: each host is a tenant with its own folder, secrets, and Twilio number, and connects with an invite code on the Allow page. `/mcp` is the one address for touring and cleaning; `/mcp/cleaner-core` stays as the cleaning address. `CLEANER_CORE_TWILIO_PHONE_NUMBER`, `CLEANER_CORE_ASSISTANT`, and `CLEANER_CORE_MCP_TOKEN` are not used there. See `docs/hosted-multitenancy.md`. |
| `TOUR_CORE_TENANTS` | Touring on the shared service | Off unless `1` or `true`. With it on (and `CLEANER_CORE_MULTI_TENANT` on), `/admin` can make an account with no properties a touring account, and each touring account runs its own Tour Core process on its number. Off, no touring process starts. Touring is parked: new accounts get properties. See `docs/hosted-multitenancy.md`. |
| `CLEANER_CORE_ADMIN_PASSWORD` | Multi-tenant Cleaner Core | The password for `/admin`, where Saad adds hosts, keeps the pool of registered text lines topped up, and makes invite codes. Unset turns the page off. Set it only in Railway's variables. |
| `CLEANER_CORE_SIGNUP` | Multi-tenant Cleaner Core | Off unless `1` or `true`. Adds Sign in and Create account to the connect page, so a host can open an account with a phone code and no `/admin` step. Needs `CLEANER_CORE_LIVE_SMS`, `CLEANER_CORE_TWILIO_VERIFY_SERVICE_SID`, `CLEANER_CORE_TERMS_URL` and `CLEANER_CORE_TERMS_VERSION`; without them the page stays invite-only. Codes go only to phones `CLEANER_CORE_SMS_ALLOWLIST` allows (`*` on the live service). With no ready numbers in the pool, Create account says no line is free. See `docs/superpowers/specs/2026-11-07-connect-page-sign-up-design.md`. |
| `CLEANER_CORE_POOL_REST_DAYS` | Multi-tenant Cleaner Core number pool | How many days a closed account's text line rests before the pool hands it to another account, so the old account's cleaner stops texting it first. A whole number of days; unset or anything else keeps 30. `0` turns the rest off, for testing with numbers no real cleaner or contact has texted. Put it back to unset before real hosts close accounts. |
| `CLEANER_CORE_TWILIO_VERIFY_SERVICE_SID` | Multi-tenant Cleaner Core | The Twilio Verify service (`VA…`) that texts and checks the sign-in code, on the `CLEANER_CORE_TWILIO_ACCOUNT_SID` account. |
| `CLEANER_CORE_TERMS_URL`, `CLEANER_CORE_TERMS_VERSION` | Multi-tenant Cleaner Core | The `https://` terms page a new account accepts, and the version recorded with the account. |
| `CLEANER_CORE_ENABLED` | Cleaner Core demo | Off unless `1` or `true`. With it off, touring texts are unchanged. `npm run cleaner:doctor` reports the flag and sends nothing. `npm run cleaner:smoke` asks the Scratch Lane owner to confirm checkout and check-in, then offers the turnover, on 555 test numbers only. With no extra operation, that smoke answers YES three times and does not text a door code. `npm run cleaner:smoke -- --reply +15555550100=STOP` repeats for each inbound reply and does not add YES. `--feed`, `--then-feed`, `--now`, `--remind`, `--fail-sends`, and `--data` drive the step C journeys. `--with-pin` asks the approved cleaner to opt in. That cleaner receives the offer, the scheduled confirmation, and the reminder, and only that cleaner's YES confirms the job. After the host says the guests have left, smoke prints a private door code as `[redacted]` to `+15555550101` only, and tells the host `Door code sent to the cleaner.` `--unapproved` and `--group` cover the step D refusals. `--google` reads a Google Calendar fixture, `--notion` reads a Notion database fixture, `--closed` syncs with no open conversation, and `--tenant scratch-court` uses 8 Scratch Court (`+15555550110`, `+15555550111`) instead of Scratch Lane. A booking on Guesty Lite and another source stays one job. `--onboard` walks a new Scratch property from its nickname through activation, and texts a cleaning offer only after that cleaner's YES and the owner's APPROVE. `--group-mode native` with `--group-capable` sends a group text when every participant has opted in. Otherwise smoke mirrors the cleaner text and labels the copy. The door code stays a private text to the approved cleaner. A reply from outside the Scratch 555 block, or any other extra argument, fails the command and sends nothing. Step G adds `npm run cleaner:health`, which reports counters and sends nothing. `--watch-freshness` holds a new offer and the door code when the feed is older than the stale threshold. That threshold defaults to three hours, three missed hourly Guesty Lite polls. Set `CLEANER_CORE_STALE_AFTER_MS` or pass `--stale-after` to change it. `--backup` and `--restore` snapshot one tenant. `--replay` and `--crash` resume without a second send. The SQLite snapshot needs Node 22. `--group-chat` seats the host from the texting setup step. He does not text YES. The approved cleaner replies YES. The door code stays a private text to that cleaner. `--group-reply`, `--confirm-times`, and `--resume` drive that thread. `CLEANER_CORE_GROUP_CHAT` is the live switch for the same thread. |
