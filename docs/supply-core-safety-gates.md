# Supply Core safety gates

These gates have to stay green before Supply Core places a live order for anyone. CI runs `scripts/ci-check.sh` on Node 22. No gate's proof reaches a real store, places an order, or texts a real phone.

| Gate | What it holds | Proof |
| --- | --- | --- |
| No card details | Every Supply Core tool input is checked: a 13 to 19 digit run that passes the Luhn check is refused before anything is saved or logged, and every tool schema is strict, so no field can carry a card number, expiry, or security code. | `test/supplyGate.test.ts`, `test/supplyOrdering.test.ts`, `test/supplyHosted.test.ts` |
| No order without go or the landlord | `record_order` is refused without a live go token bound to that cart, or the landlord's approval through `approve_cart`'s code. An expired cart can't be approved or recorded. | `test/supplyOrdering.test.ts` |
| Caps and price jumps | `check_cart` decides the per-order and monthly caps, a price more than the threshold over the last price paid, a missed deadline, and stop-at-checkout mode in code. Grok's words can't turn a hold into go. Two open carts can't hold the same item. | `test/supplyGate.test.ts`, `test/supplyOrdering.test.ts` |
| Cleaner text | A cleaner's text only marks list items low. `report_low` takes item ids, not words; it can't add an item, set a product, store, link, or cap, approve a cart, or order anything not on the list. | `test/supplyOrdering.test.ts` |
| DONE supplies question | Goes only to the approved cleaner (or the group addressed to them), only with Supply Core on and active, never carries the door code, and follows the same per-account texting consent as every cleaning text. Also a gate in `docs/cleaner-core-safety-gates.md`. | `test/cleanerSupplyAsk.test.ts`, `test/cleanerSupplyDesk.test.ts` |
| No real shopping in tests | Tests use made-up stores, `https://shop.example/…` links, and made-up order numbers, and 555 numbers only. Calendar reads are stubbed. | every `test/supply*.test.ts` |
| Checkouts from a clean read | By-bookings items count only checkout dates from a read where every one of the property's booking calendars (in its hub, shared with Cleaner Core) read cleanly. After a failed read the last good dates stay, and by-bookings items wait for the next good read. | `test/hub.test.ts`, `test/hubSupply.test.ts`, `test/supplyOrdering.test.ts` |
| Tenants apart | Two tenants never see each other's lists, orders, or spending. A supplies tenant's number answers no text. | `test/supplyHosted.test.ts` |

## Separate bots (#250)

Behind the account's Separate bots switch on `/admin` (`bots`), off by default, on Grok Bot only. Each connection carries the job of the address it signed in at (`/mcp`, `/mcp/cleaner`, `/mcp/supply`, `/mcp/fixer`), and the server lists, refuses and wakes by job. A core's job is held by its own bot once that bot is connected and has saved its Alerts routine. Until then, and whenever that bot goes away, the Property Core connection holds it. The tests use made-up properties, 555 numbers, made-up codes and keys and a stubbed routine; none reaches a lock, a store, a pro or a phone. Design: `docs/superpowers/specs/2026-11-22-bot-per-core-design.md`.

| Gate | What it holds | Proof |
| --- | --- | --- |
| Off means unchanged | With the switch off, or with only `/mcp` chats on the account, every tool is listed, answered and woken exactly as before. A core's address is refused with the switch off, and the invite code isn't used up. | `test/botJobsHosted.test.ts` ("an account with one bot lists what it lists with the switch off"); `test/botJobsHosted.test.ts` ("refuses a core address with the switch off, without using the invite"); `test/botJobsHosted.test.ts` ("with one bot, get_state is what it is with the switch off"); `test/botJobsHosted.test.ts` ("with one bot, report_low and open_job answer as on master") |
| The landlord's yes, from the Supply job only | `approve_cart` is listed for and answered to a chat that has the Supply job, and no other. The Cleaner Core and Fixer Core bots are refused on the call. | `test/botJobsHosted.test.ts` ("each core's own yes is refused from every other core's bot, on the call"); `test/botJobsHosted.test.ts` ("each core's bot lists exactly its own tools") |
| A filing reply carries no question | The Cleaner Core bot's `report_low` takes item ids with `source: "cleaner"` only and is written once. Its reply is `{ filed: true }` and one line that says who orders: no cart, price, cap or approval question. The wake-up for it names no item. | `test/botJobsHosted.test.ts` ("report_low from the Cleaner bot is written once, wakes the Supply bot, and carries no question"); `test/botJobsHosted.test.ts` ("a filing into a core with no bot of its own names the Property Core bot and wakes its routine"); `test/botJobsHosted.test.ts` ("a filing is refused where the owning core isn't on") |
| A filing's wake-up is retried | A wake-up for a filing that doesn't go through is kept by time only and tried again every 5 minutes, until it goes through, the owning bot calls on its own, or two days pass. Supply Core's check runs once a day, so its bot is called quiet only after 26 hours without a call, not 2.5. | `test/botJobsHosted.test.ts` ("a filing's wake-up that doesn't go through is tried again by the clock, until it does"); `test/botJobsHosted.test.ts` ("a filing's wake-up isn't tried again once its bot has checked in, or after two days"); `test/botJobsHosted.test.ts` ("a Supply Core bot that checked in earlier today isn't called quiet: its check runs once a day"); `test/botJobsHosted.test.ts` ("a Supply Core bot quiet for over a day with an alert waiting is told about too, and the alert stays its own") |
| Package alerts, once | Where the Supply Core bot holds its job, a package not seen reaches it through `check_alerts`, shown once, after a wake-up with no content. An alert older than two days is let go. When the last core bot goes, an alert a bot was woken for and never read goes to the host's notes instead. The routine's upload link is single-use, lasts 30 minutes, and saves to the calling chat only. | `test/botJobsHosted.test.ts` ("a property with only Supply Core on gets its package alert through check_alerts"); `test/botJobsHosted.test.ts` ("an alert with no routine waits and is shown once"); `test/botJobsHosted.test.ts` ("an alert older than two days is let go, not shown late"); `test/botJobsHosted.test.ts` ("an alert a bot was woken for and never read goes to the host's notes when the last core bot goes"); `test/botJobsHosted.test.ts` ("the upload link is single-use and saves to the caller only") |
| The check is on the call | A job only takes tools away. A tool another job owns is refused on the call, before any desk runs, with a line that names the bot to open; hiding it from the list is not the gate. A routine left behind in the Property Core chat is refused the same way. A core's connection made before the switch went off lists nothing and is refused. | `test/botJobsHosted.test.ts` ("a core's bot is refused another job's tool before any desk"); `test/botJobsHosted.test.ts` ("a left-behind routine's check is refused before the desk"); `test/botJobsHosted.test.ts` ("a core connection made before the switch went off lists nothing and is refused") |
| A second bot replaces the first | One bot per core. A second bot at the same address ends the first one's sign-in and deletes its saved routine. A core's connection is never the primary, and a yes asked about one bot never removes the one that replaced it. | `test/botJobsHosted.test.ts` ("a second Fixer Core bot replaces the first"); `test/botJobsHosted.test.ts` ("the connection carries its job and never becomes primary"); `test/botJobsHosted.test.ts` ("a confirmation asked for one Fixer Core bot doesn't remove the one that replaced it") |
| The job comes back | The holder is worked out on each request, so nothing is saved for it. The Property Core connection holds the job again when the bot's grant ends, when it's disconnected (what `/admin`'s Disconnect does), when the switch goes off, and when the host tells the Property Core bot the core's bot is gone (`remove_bot`, two calls). | `test/botJobsHosted.test.ts` ("the job comes back when the bot's grant ends"); `test/botJobsHosted.test.ts` ("the job comes back when the bot is disconnected"); `test/botJobsHosted.test.ts` ("the job comes back when the switch goes off"); `test/botJobsHosted.test.ts` ("remove_bot hands the job back after the host's yes") |
| Accounts apart | A core's bot reaches only its own account's properties. | `test/botJobsHosted.test.ts` ("one account's bot never reaches another account") |
